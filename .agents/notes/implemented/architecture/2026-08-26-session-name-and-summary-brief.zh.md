# Agent Note: 会话命名——模型同时写出名称与摘要，而非提示词前缀

Status: implemented

[English](2026-08-26-session-name-and-summary-brief.md) | 中文

## 问题

会话名称来自确定性回退：用户提示词的开头几个词。回退保证名称永不缺失，但作为产品名称它有两处失败——它复述措辞而不是描述意图（"Reply with exactly TITLE_DONE. Do" 什么也说明不了），而且侧边栏没有任何办法在不打开会话的情况下了解其内容。

模型提供方路径早已存在，但实际部署中几乎总是输给回退：辅助调用的预算是 `maxOutputTokens: 64`，而路由经过具备推理能力的路由（部署默认路由会输出推理块）。仅推理轨迹就会耗尽上限，每次调用都以 `max-tokens` 结束，服务便一直保留回退。功能存在、已配置、却形同虚设。

## 决策

**模型产出单行一个 JSON 对象，含两个字段——`name` 与 `summary`。** 一次辅助调用同时满足两个产品需求：侧边栏标题不再复述提示词，悬浮卡可以显示一句意图描述而不是被剪裁的提示词。共享辅助组件（`session-title-llm`）把它作为 *brief* 变体持有：与标题相同的路由解析、消息封装、请求记录、时限组合和流组装；不同的指令、输出解析与验收。`generateSessionBriefWithLlm()` 宽容地解析 JSON（通过切出最外层大括号忽略围栏输出与周围的推理文本），规范化两个字段，按码点边界把摘要截断到 `maxSummaryBytes`，并在返回前追加仅写入日志的 `session/summary` 事件；标题服务随后追加提供方标题，因此日志中摘要总是紧邻与其一同派生的标题之前。

**摘要走投影系统，而不是新的传输路径。** `session/title/src/types.ts` 在两个投影合并中紧邻 `title` 声明 `summary` 键；brief 注册器注册该单元（字符串或 null 状态、恒等 wire 视图），客户端树把 `projectionValues.summary` 复制到行节点供悬浮卡使用。不改动会话列表 RPC，不新增客户端服务，也不做逐客户端拉取。

**推理轨迹拥有自己的配置行，且随附默认值假设它存在。** `maxOutputTokens` 被文档化为「推理轨迹加可见回答」的预算，基础 bundle 行现在附带 1024 并写明注释。把它设成「刚好超过标题长度」会在推理路由上无声地废掉整个功能；在思考关闭时设得宽松毫无代价，而这正是 DeepSeek 适配器对该用途的行为。

## 后果

first-prompt 提供方现在请求并持久化两个值；它的配置增加三个必填字段（`targetSummaryWords`、`targetSummaryCjkCharacters`、`maxSummaryBytes`），既有组合必须补齐这些字段，否则加载时响亮失败。已显式设置 `provider`／`model` 覆盖项的部署无需改动即可继续工作；依赖路由继承的部署只有在其路由会推理时才需要更大的 token 上限。在此变更前已命名的会话保留其回退标题，直到显式刷新或之后的 all-prompts 修订；运行中的 GUI 需要重建 web bundle 并重启服务器后才会呈现悬浮渲染。格式错误的 JSON 回答会拒绝整个修订——不接受只含裸名称的部分结果——因为摘要正是这个变体的意义所在，且其失败路径与其他任何提供方拒绝完全一致（保留回退、记录警告）。

## 已考虑的替代方案

- **两次调用（先标题后摘要）**——为同一段对话把辅助延迟与成本翻倍，还会让两个答案互相矛盾。
- **本地从标题推导摘要**——五个词的名称无法在不编造模型从未产出的内容的情况下扩展回意图。
- **用独立提供方插件持有摘要**——标题服务的单提供方席位会迫使部署在共用同一触发、同一节奏与同一路由决策的两个功能之间二选一。
- **结构化输出适配器代替文本内 JSON**——辅助组件经由 `ctx.llm.stream()` 对接任意适配器；纯文本 JSON 保持约定与适配器无关，且解析本就容忍围栏或被推理包裹的回答。
